Two patterns cover every tool above. Either the editor is a separate pane with its own keyboard and its own controls to the left of it, or the editor replaces the all-track grid for one instrument. No tool widens the track header to make room for the editor, which is what Keyboardia does today, and none inserts an editor between two track rows.

Constraints the arrangement has to respect

  • Column alignment. Every step column, in every row and in the roll, sits on a 39px pitch (36px cell + 3px ordinary gap), with 8px extra at each 16-step page boundary. The 11px page band is shared by the ruler, cells, property lanes and dock. The adopted keyboard and control column are both 154px on desktop, with the common 8px gap before step 1 at x=162px. The dock column contains an 18px range rail and 136px keyboard; mobile uses 216px and x=224px.
  • Row rhythm. Track rows repeat at one height. The eye scans down a column to see which instruments hit a beat together. Anything inserted between rows that is not a row of cells breaks the scan.
  • Tessellation. Rows are the same width and height and butt against each other, so the grid reads as one surface. A drawer under one track, and equally a 400px roll under one track, splits that surface in two.
  • Row width is load-bearing. Changing the control column's width moves the drop target for drag-reorder during playback, which the project's lesson 62 records as fragile. Moving width between left and right of the row keeps the total, which is a different proposition from changing it.
  • Discoverability. Transpose and step count are the two controls people reach for while composing. Hiding them costs more than hiding pattern tools or the instrument picker.
  • Shared horizontal scroll. All rows and the editor scroll together, and sticky columns on the left (or right) must be children of that one scroller.

Adopted consistency contract · revised audit targets

Lesson 31: use the app's single JavaScript display-mode decision. Desktop when width ≥768 and height ≥500; otherwise landscape when height <500 or width >height; otherwise portrait. CSS reads root data-display-mode from that decision, without independent sequencer orientation/height queries. Boundary probes: 767 × 768 portrait; 768 × 768 and 769 × 768 desktop; 768 × 499 landscape. Other examples: 1024 × 500 desktop; 700 × 600 landscape; short portrait height 499 landscape.

  • Desktop targets. Left 154 = grip 12 + gap 4 + body 130 + padding 8. Identity 24 + gap 2 + controls 24 = 50; padding 4 above/below gives row 58, with 2px gap giving 60px pitch. Five controls are 24 × 24; group gaps total 10px.
  • Mobile targets. Left 216 = name 64 + M 44 + S 44 + Edit 44 + three 4px gaps + padding 8. Single-line row 48; pitch 50. Portrait mode at width <768 and height ≥500 shows a consumption placeholder, with no rows, dock or editing.
  • Dock chrome. Desktop header 84 = visible track/step context 32 + tabs 32 + padding 16 + gap 4; tools 48 with controls 32, status 24 and top border 1. Total desktop dock heights are 409 compact / 589 tall (body 252/432). Mobile expanded sheet is fixed inset 8 in the main mock: header 88 (two 44px rows without vertical padding/gap), tools 48 (44px controls + 4px padding), status 16 and borders 2; body fills the remainder, at least 150 at 568 × 320. Mobile keys use an independent 84px column (18 rail + 66 keys) and body scroller with the same stepX/page mapping and bar.beat labels in the existing 16px status line at left = 92 + stepX(s) − body.scrollLeft, plus an always-visible selected-step heading/readout; returning preserves row scroll. Timeline labels consume no body height. These embedded previews show the same inset within each card's viewport.
  • Toolbar parity. Notes: scale, scale lock, octave, Ghosts, Range, Default velocity, Fit comparison, Zoom out/in, Pan, Loop start/end inputs and Clear loop (32px desktop / 44px mobile). Track: instrument, step count, transpose and pattern tools; instrument/pattern previews stay in the body, lane disclosure stays on the row, and Copy/Paste/Clear/Delete stay exclusively on the row. Selected-step heading and pitch/velocity readout remain visible in every pane; main stepCursor updates both. Step has a toolbar Step picker: 32px desktop / 44px mobile, an operable alternative to tiny notes; desktop satisfies the 24px target minimum without claiming a 44px body selector. All editing and audition controls here are disabled, explicitly labelled integration previews; only navigation and keyboard hover labels work.
  • Pitch and viewport. Full chromatic MIDI 12..108; scale lock preserves existing off-scale notes. Future hover ghost, tooltip, row highlight and commit share the snapped pitch. Pitch zoom 2..36, default 18; solid/ghost heights are max(1px, 14/18 × H) and max(1px, 12/18 × H), centered within each row with radius min(3px, half actual height). Explicit main-mock Fit comparison chooses fractional H = clamp(B/(hi−lo+5), 2, 36), including enabled ghosts and two rows of padding per side; initial/switch Fit caps at 18, while ghost-toggle Fit uses the 36px ceiling. Fit reveals the padded upper edge within scroll bounds; manual zoom preserves the viewport center. This Fit implementation is present in the main mock; the layout-card control remains disabled. Desktop body detents 252/432 remain stable across melodic panes and drum Step/Track. Keyboard white keys use the main mock's half-row span algorithm (source near line 620), with black keys overlaid. White root/fifth labels use --piano-key-label; valid keys outside the recommended range stay at full brightness. Root/fifth hue and out-of-recommendation decoration belong on grid rows and the bracket.
  • Presence, contrast and state. Cells/bars share the local velocity fill formula, unlocked 1.0. Constant --note-presence-outline: #b8b8b8 keeps bars visible at zero; foreground is recalculated from each fill (dark on bright, white on dark). --color-info: #3498db; focus uses --info-text: #5eb3ea. Informative labels use --muted. Keep the current column across Notes/Step; ♪ is active only in Notes. Header rebuilds restore focused data-track/data-pane; pane switches keep the mounted grid and scroll.
  • Step capabilities and operations. Pitch and Volume apply to all tracks, including drums; Notes alone is melodic-only. The main one-shot drum preview cannot sustain ties, so its Tie control remains visibly disabled with an explanation; the real app uses instrument capability and inherited-value rules for Tie and envelope stages. Activate/Deactivate changes activation while preserving locks; Erase step clears activation and locks; Clear lock leaves activation unchanged. These controls are disabled integration previews here, including envelope examples that do not imply universal drum support.
  • Future mutation and Escape contract. Explicit placement/paint on an inactive step sets the requested pitch and tie:false while preserving volume/envelope fields; ordinary activation toggles and tie extension preserve stored fields. Dock Delete addresses only the selected range first, otherwise only the cursor/bar note. One accepted pointer ID owns a gesture; Pan movement/mode changes cancel pending holds. Home/End reveal first/final steps beyond the sticky keyboard without changing row scroll. Shared inactive-step context uses stored/default effective pitch and volume; live announcements include effective volume and tie inheritance. After menus/rename consume their own Escape, successive Escape cancels drag, then copy, then closes the dock only with dock focus, before selection handling; the range survives. Outside-dock selection handling remains. These are app acceptance requirements; this companion does not implement mutations or Escape arbitration.
  • Initial mobile Pan. Each newly opened mobile editor starts with Pan pressed and touch-action:auto; initial swipes scroll without editing. Explicitly switch Pan off to Draw; pane/track switches within the open editor retain the chosen mode. These disabled cards show the initial Pan state as a preview, with editing controls still disabled.
  • Access and row actions. Name Enter/Space opens Track immediately; mouse single-click waits 200ms for double-click Rename in the main workflow. Copy/Paste/Clear/Delete stay on the row. Their normal-flow width and trailing padding reserve end scroll space; a muted edge identifies the sticky area. In landscape below 440px viewport width, actions are static at the far end of the horizontal row so Edit stays unobscured; at width ≥440 they remain sticky-right. Keep left 216, row 48 and pitch 50, with no additional sheet or row height and the same JavaScript/root display mode. Verify every far column becomes unobscured when scrolled right. The main loop ruler is a keyboard focus group, not sliders; main-mock Loop start/end inputs and Clear loop live in the Notes toolbar, 32px desktop / 44px mobile, shown here as disabled previews.
  • Audit status. Rankings are design hypotheses, with discoverability and engineering risk pending verification. Future app acceptance covers all 14 findings in the storyboard. Historical candidates are labelled and exempt from revised target geometry; they are alternatives, not compliant implementations.

Four tracks: Lead and Bass are melodic, Kick and Hat are drums. The person has opened the roll for Lead and then for Bass. Each mock shows what the screen holds at that moment.
