Keyboardia · Pitch panel · Design brief

Piano roll dock

Proposal only · PR #127 changes spec and mocks, with application integration deferred to the phases below. The decision from the layout research, worked through: how the dock layers over the grid, what moves and what stays still in each scenario, which gestures it answers to, how it is documented in this project's own format, and what it changes for the other per-track panels, mobile, large pieces and the open work on GitHub.

1. Decision

The note editor leaves the track list. On desktop, one editor dock sits under the sea of cells, inside the shared horizontal scroller, pinned to the bottom while tracks scroll above it. Expanded mobile uses the separate editor sheet described below. It shows one track at a time, chosen by the track's pitch toggle, its name, or a tab in the dock. Every track, including drums, has a tab and can open Step or Track; Notes is available only for melodic tracks. Other melodic tracks appear as ghost notes. The desktop control column is a two-line block, 154px wide, matched by the dock's left panel (18px range rail + 136px proportional keyboard). Its 84px header exposes track/step context above tabs; a fixed 48px toolbar uses 32px controls. Expanded mobile uses a separate editor timeline: fixed inset 8px, header 88px, tools 48px with 44px controls, status 16px and borders 2px, leaving a 150px body at 568 × 320. Mobile keys use 84px (18px rail + 66px keys), independent of the 216px single-line row controls. Rows never gain or lose a panel between them.

Three things pinned this choice: the per-track roll fails the two-rolls-open test, every reference tool keeps editors out of the track list, and rows stay contiguous. The row diet changes the control width once when it ships; opening, closing or switching the dock never changes it. That one width change requires lesson 62's drag-reorder checks.

The dock is the generalised ParameterLockEditor that C-1 wanted to keep, moved from "below its row" to "below the grid" so that two of them can never stack. That amendment should be written into AFFORDANCES before either lands.

2. Layering

Every surface gets a named layer so that stacking is a decision, not an accident of DOM order. Today's sticky control column is at z 3 and overlays at 100; the dock slots between.

Rules the layers encode

  • Only the dock's height changes layout. Opening it takes space from the bottom of the scroller. Nothing between two track rows ever changes size.
  • One left edge. The desktop 154px column starts at x=0; gap 8 places ruler, cells, dock grid and lanes at x=162px. An 18px rail precedes the 136px keyboard. Mobile row left is 216px; the expanded editor has an independent 84px key column and timeline.
  • Desktop shared scroller. The dock shares .tracks horizontal scroll, so step N is at the same x in the ruler, every row and the dock. Pitch scroll is independent. Expanded mobile also has independent horizontal body scroll, the same stepX/page mapping and explicit step/selection context; return restores the row timeline unchanged.
  • State lives on the control-block edge, class lives on the name. Docked state uses a 2px accent edge on the control block only. Active chips and ♪ use the accent; the category tick keeps the track's category colour.
  • Transient layers never take pointer events. One hit layer in the dock computes step and pitch from coordinates, as the prototype does.

5. How to document it

The project has a working format for exactly this kind of decision, visible on the roadmap branch: a spec in specs/, static HTML mocks in specs/mocks/, a postmortem-style lessons file when a surface is replaced, and a lesson in docs/LESSONS-LEARNED.md when a constraint is discovered. Follow it.

  1. specs/PIANO-ROLL-DOCK.md, status Proposal, with the headings the other UI specs use: The Problem, The Proposal, Visual Representation, Interaction Design, UI Philosophy Alignment table, What We Remove, Multiplayer Considerations, Implementation Phases, Alternatives Considered, Visual baseline safety, Non-goals, Open Questions, References. The research page and this brief become its content. The six ranked arrangements and the two-rolls test go under Alternatives Considered, with the modal recorded under "Decided against", as #121 does.
  2. specs/mocks/piano-roll-dock.html: the interactive prototype, checked in as the roadmap branch checks in its storyboards. Specs cite mocks by file; the chosen contract must agree across the normative spec and all three companions; measured mocks supply evidence rather than a compliance claim.
  3. Constraints as a table with a source each. Column alignment, row rhythm, tessellation, lesson 62, shared scroller, mobile modes, published mode, 64KB message cap if dock state ever syncs. One row per constraint, one file:line or lesson number per row, so a later reader can check whether it still holds.
  4. Trade-offs as a ledger, not prose. What the dock gives up (the roll is not under its row; one editable track at a time) against what it buys, each with the scenario that exposed it. Future readers argue with ledgers; they ignore paragraphs.
  5. Amend AFFORDANCES.md C-1 and C-4 in the same change, so the two specs cannot disagree.
  6. A lesson when the build teaches one. The loop ruler's "in-grid or content-bearing" rule is the model; the first candidate here is "an editor is not a lane: lanes tessellate, editors dock".
  7. PR template already asks What changed / Why / Verification / Risk. Risk should name the reorder suite and the visual baselines explicitly.

6. Consequences

6.1 The other panels and drawers

A track row today can stack seven surfaces below it, each with its own useState and no accordion: the landscape TrackDrawer, the instrument picker, PatternToolsPanel, VelocityLane, the legacy InlineDrawer, an always-on FM panel, the pitch panel, and the ParameterLockEditor strip. #87 adds an envelope editor to the strip. This is the sprawl the affordance spec counted as nine reveal mechanisms. The dock is the chance to tidy it, and the tidy has a rule: rows of cells and immediate row actions stay inline; editors dock.

6.2 Mobile

Lesson 31: one JavaScript decision mirrors the existing orientation decision in app/src/hooks/useDisplayMode.ts exactly. Desktop if width ≥768 and height ≥500; otherwise landscape if height <500 or width >height; otherwise portrait. CSS reads root data-display-mode from that same decision. Sequencer orientation/height media queries must not independently select a mode.

  • Portrait at width <768px, portrait orientation and height ≥500px is consumption only: hide the full sequencer, render no rows or dock and show a visible rotate-to-edit placeholder. Other portrait sizes do not inherit this blanket exclusion.
  • Landscape row uses left 216px: name 64 + M/S/Edit each 44 + three gaps 4 + padding 8. Single-line row 48, pitch 50. Edit opens supported Step/Track for drums and Notes for melodic tracks; maintain lane access and all shipped actions. Below 440px viewport width, row actions are static at the far end of the horizontally scrolling row, keeping Edit unobscured; at width ≥440 they remain sticky-right. This width rule applies only within the existing JavaScript landscape mode; it adds no sheet and changes no row height or display-mode decision.
  • Expanded editor sheet is fixed inset 8px: header 88 (two 44px rows, no vertical padding/gap), toolbar 48 (44px controls + 4px padding), visible status 16 and borders 2. --dock-grid-h: calc(100dvh - 170px) fills the remaining body, giving 150px at 568 × 320. Every newly opened mobile editor starts with Pan enabled (aria-pressed=true, touch-action:auto), so initial swipes scroll without mutating notes; switch Pan off explicitly to Draw. Pane/track switches within the open editor retain its mode. Body must not collapse when switching to drum Step/Track.
  • Separate editor timeline uses key column 84 = rail 18 + keys 66 and its own horizontal body scroller. Keep desktop stepX/page mapping, an always-visible selected-step heading/readout and bar.beat labels in the existing 16px status line, synchronized to 92 + stepX(s) − body.scrollLeft without reducing the 150px body. Desktop retains shared horizontal scroll and alignment; expanded mobile gives keys room and returns to unchanged row scroll.
  • Preview scope is explicit: these layout cards embed the sheet within a viewport and show the disabled editing/audio status on mobile. Actual fixed positioning, safe areas, focus return, orientation transitions and touch gestures require app verification.

6.3 Very complex pieces

  • Sixteen tracks, 128 steps. The dock renders one track as bars, not 4,600 buttons, so it is cheaper than today's roll. Sixteen rows at 60px pitch plus dock chrome and a 252px body exceeds most viewports; the tracks scroll under the sticky dock, which is the DAW behaviour.
  • Polymeter. Rows end at different widths. The dock's grid is the docked track's length, with the same page dividers. Ghost notes from a track of a different length repeat modulo that length, drawn lighter, so the ghost is truthful about what will sound (the loop ruler postmortem's "truthful per-track rendering").
  • Many melodic tracks. Ghosts are per-track toggles, on by default for the two nearest melodic tracks and off beyond that, so a sixteen-track piece does not become a thicket.
  • Any length (#119) changes nothing in the dock except that page dividers stop coinciding with track ends.
  • Patterns and song mode (#121). The dock edits the current pattern. A queued switch re-renders the dock at the boundary. Song playback is a sequence of such re-renders. The dock should display the pattern name in its title from day one so that the field exists when patterns do.

6.4 Multiplayer and data

  • Dock state (which track, which pane, ghost toggles, pitch scroll) is local, as every panel is today. It never syncs, so the 64KB message cap is untouched.
  • Every dock edit uses reversible domain mutations: preserve parameter locks on toggle/re-pitch/tie edits, validate collisions before committing and roll back the complete gesture on failure. The MCP note surface in #92 should share those operations, so an agent-written melody and a dock-drawn melody are the same data.
  • The focus slice already exists in the store with no UI dispatching it. "Docked track" can be that slice, which keeps the reducer honest without adding a new one.
