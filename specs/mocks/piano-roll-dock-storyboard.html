Keyboardia · Pitch panel · Design brief

Piano roll dock

Proposal only · PR #127 changes spec and mocks, with application integration deferred to the phases below. The decision from the layout research, worked through: how the dock layers over the grid, what moves and what stays still in each scenario, which gestures it answers to, how it is documented in this project's own format, and what it changes for the other per-track panels, mobile, large pieces and the open work on GitHub.

1. Decision

The note editor leaves the track list. One editor dock sits under the sea of cells, inside the same horizontal scroller, pinned to the bottom of the viewport while the tracks scroll above it. It shows one track at a time, chosen by the track's pitch toggle, its name, or a tab in the dock. Every track, including drums, has a tab and can open Step or Track; Notes is available only for melodic tracks. Other melodic tracks appear as ghost notes. The control column is a two-line block, 134px wide, and the dock's left panel fills that same width (18px range rail + 116px keyboard), so the dock and track control columns align. The dock's own controls sit in a fixed 48px toolbar under its header, on one horizontally scrollable line in every pane. Rows never gain or lose a panel between them.

Three things pinned this choice: the per-track roll fails the two-rolls-open test, every reference tool keeps editors out of the track list, and rows stay contiguous. The row diet changes the control width once when it ships; opening, closing or switching the dock never changes it. That one width change requires lesson 62's drag-reorder checks.

2. Layering

Every surface gets a named layer so that stacking is a decision, not an accident of DOM order. Today's sticky control column is at z 3 and overlays at 100; the dock slots between.

z 0
Grid surfaceTrack rows, step cells, page dividers. The only layer that scrolls in both axes.
z 1
In-row lanesPitch contour marks inside melodic cells, velocity lane rows (AFFORDANCES N3). Rows of cells, same column grid, tessellate.
z 2
Row statePlaying outline, remote-change flash and selection. Docked state is a 2px accent edge on the control block only; it never outlines the cells or the full row.
z 3
Sticky chrome, left134px control column and ruler spacer, with the docked edge on the control block.
z 5
Sticky chrome, topLoop ruler, moved into the scroller on the step pitch (per the loop ruler postmortem's "in-grid or content-bearing" rule).
z 6
Editor dockSticky to the scroller's bottom edge. Its control panel is sticky-left at z 7 inside it. Holds three panes: Notes, Step, Track.
z 8
Transient, inside the dockGhost note under the pointer, hover crosshair, drag preview, tooltip chip. Pointer-events none.
z 10
PlayheadsOne line in the ruler, one across the dock grid, plus the existing per-cell outline. Driven by the scheduler's position, never animated with CSS.
z 100
Global overlaysQR, shortcuts, the planned bottom sheet (C-7). Never used for the roll.

Rules the layers encode

  • Only the dock's height changes layout. Opening it takes space from the bottom of the scroller. Nothing between two track rows ever changes size.
  • One left edge. The 134px column starts at x=0; the common 8px gap places the ruler, cells, dock grid and property lanes at x=142px. Inside the dock column, an 18px range rail precedes the 116px keyboard.
  • One scroller. The dock shares .tracks horizontal scroll, so step N is at the same x in the ruler, every row and the dock. Vertical scroll of the dock's pitch range is the dock's own.
  • State lives on the control-block edge, class lives on the name. Docked state uses a 2px accent edge on the control block only. Active chips and ♪ use the accent; the category tick keeps the track's category colour.
  • Transient layers never take pointer events. One hit layer in the dock computes step and pitch from coordinates, as the prototype does.

5. How to document it

The project has a working format for exactly this kind of decision, visible on the roadmap branch: a spec in specs/, static HTML mocks in specs/mocks/, a postmortem-style lessons file when a surface is replaced, and a lesson in docs/LESSONS-LEARNED.md when a constraint is discovered. Follow it.

  1. specs/PIANO-ROLL-DOCK.md, status Proposal, with the headings the other UI specs use: The Problem, The Proposal, Visual Representation, Interaction Design, UI Philosophy Alignment table, What We Remove, Multiplayer Considerations, Implementation Phases, Alternatives Considered, Visual baseline safety, Non-goals, Open Questions, References. The research page and this brief become its content. The six ranked arrangements and the two-rolls test go under Alternatives Considered, with the modal recorded under "Decided against", as #121 does.
  2. specs/mocks/piano-roll-dock.html: the interactive prototype, checked in as the roadmap branch checks in its storyboards. Specs cite mocks by file; the mock is the single source for geometry numbers.
  3. Constraints as a table with a source each. Column alignment, row rhythm, tessellation, lesson 62, shared scroller, mobile modes, published mode, 64KB message cap if dock state ever syncs. One row per constraint, one file:line or lesson number per row, so a later reader can check whether it still holds.
  4. Trade-offs as a ledger, not prose. What the dock gives up (the roll is not under its row; one editable track at a time) against what it buys, each with the scenario that exposed it. Future readers argue with ledgers; they ignore paragraphs.
  5. Amend AFFORDANCES.md C-1 and C-4 in the same change, so the two specs cannot disagree.
  6. A lesson when the build teaches one. The loop ruler's "in-grid or content-bearing" rule is the model; the first candidate here is "an editor is not a lane: lanes tessellate, editors dock".
  7. PR template already asks What changed / Why / Verification / Risk. Risk should name the reorder suite and the visual baselines explicitly.

6. Consequences

6.1 The other panels and drawers

A track row today can stack seven surfaces below it, each with its own useState and no accordion: the landscape TrackDrawer, the instrument picker, PatternToolsPanel, VelocityLane, the legacy InlineDrawer, an always-on FM panel, the pitch panel, and the ParameterLockEditor strip. #87 adds an envelope editor to the strip. This is the sprawl the affordance spec counted as nine reveal mechanisms. The dock is the chance to tidy it, and the tidy has a rule: rows of cells stay inline, everything else docks.

Pitch panel (ChromaticGrid, PianoRoll)Dock, Notes paneThe decision

The row diet ships atomically with working desktop Track controls in phase 3 as a two-line control block: identity on line one (category tick, name, transpose readout), state and disclosure on line two (mute, solo, then badge, pitch toggle, lane toggle). Two 17px lines with a 2px gap make 36px, inside a 44px row with 4px padding above and below; the 2px row gap gives a 46px pitch. The column is 134px (12px grip + 4px gap + 110px body + 8px horizontal padding). Line two is five 20 × 17px items: 2px within groups, 4px between groups. The width change is the lesson 62 exposure, taken once, in phase 3 with the working Track replacement; the shell preserves original controls.

6.2 Mobile

  • Portrait is consumption. No rows render, so no dock. Unchanged.
  • Landscape is where the dock fixes a real gap. The TrackDrawer's pitch, velocity and pattern buttons change state today, but CSS force-hides every panel container, so nothing opens. The mobile spec's feature matrix promises the chromatic grid in landscape. A bottom dock at roughly 45% of the height, with the keyboard aligned to the 134px control column and Notes for melodic tracks, delivers it. Drum tracks use Step and Track. Identity 17px + gap 2px + controls 28px + padding 1px makes a 48px row; with a 2px gap the pitch is 50px. Dock controls are 28px high with 4px radii; the toolbar remains 48px and scrolls horizontally. Reserve enough bottom space for rows to clear the dock.
  • The landscape scroll model is the constraint. Below 768px each row's step area scrolls on its own, so the dock cannot align with every row. It aligns with the docked row only, by syncing the two scrollers. That should be stated in the spec as a known difference from desktop rather than hidden.
  • Tablet is desktop above 768 wide and 500 tall, so the desktop dock applies.

6.3 Very complex pieces

  • Sixteen tracks, 128 steps. The dock renders one track as bars, not 4,600 buttons, so it is cheaper than today's roll. Sixteen rows at 46px plus a 300px dock exceeds most viewports; the tracks scroll under the sticky dock, which is the DAW behaviour.
  • Polymeter. Rows end at different widths. The dock's grid is the docked track's length, with the same page dividers. Ghost notes from a track of a different length repeat modulo that length, drawn lighter, so the ghost is truthful about what will sound (the loop ruler postmortem's "truthful per-track rendering").
  • Many melodic tracks. Ghosts are per-track toggles, on by default for the two nearest melodic tracks and off beyond that, so a sixteen-track piece does not become a thicket.
  • Any length (#119) changes nothing in the dock except that page dividers stop coinciding with track ends.
  • Patterns and song mode (#121). The dock edits the current pattern. A queued switch re-renders the dock at the boundary. Song playback is a sequence of such re-renders. The dock should display the pattern name in its title from day one so that the field exists when patterns do.

6.4 Multiplayer and data

  • Dock state (which track, which pane, ghost toggles, pitch scroll) is local, as every panel is today. It never syncs, so the 64KB message cap is untouched.
  • Every edit the dock makes is an existing mutation: toggle step, set parameter lock. The MCP note surface in #92 should share those operations, so an agent-written melody and a dock-drawn melody are the same data.
  • The focus slice already exists in the store with no UI dispatching it. "Docked track" can be that slice, which keeps the reducer honest without adding a new one.

Build order

PR #127 covers phase 1 only: specification and mocks. These are future implementation phases, not completed app work. Keep each original entry point until its replacement works.

  1. Spec and mocks. Reconcile these companions to specs/PIANO-ROLL-DOCK.md; carry the C-1 / C-4 amendment. No app code.
  2. Desktop dock shell and access. Every-track tabs, capability-aware panes, 2px control-block edge, animation, Escape, reserved dock space, fixed 48px toolbar and 28px / 4px chrome. Preserve all valid absolute pitches and off-scale notes. Keep the original row template, original Track/Step controls and landscape paths reachable.
  3. Desktop Track pane and row diet, together. Deliver working transpose, step count, instrument, pattern tools, copy / clear / delete, supported FM controls and lane disclosure for all tracks, including drums. Only then replace desktop originals with the 134px column, 17px lines, 44px rows and 46px pitch; update every spacer/offset and verify drag/auto-scroll against a real Worker. Keep editable transpose until its replacement works. Landscape keeps its old path.
  4. Shared rendering and column geometry. Bars/ties, 18px pitch rows, 14px bars, 18px range rail / 116px keyboard, ruler, validated draw/drag, 252px / 432px detents and shared 8px leading gap / 11px page bands. Introduce canonical CSS tokens and the shared cell/bar velocity formula together: unlocked 1.0, no white fill or volume badge. Preserve MIDI 12..108 and scale-lock visibility/bounds.
  5. Step pane cutover. Complete supported locks and #87's envelope editor for all track types; verify selection, reset, editing and read-only behavior. Remove the desktop strip only when its replacement works. Preserve the landscape path.
  6. Ghosts and contour cutover. Truthful absolute-pitch ghosts and melodic pitch/tie contours. Remove pitch/tie badges when contours land; retain only velocity colour, contour and the purple lock border.
  7. Atomic landscape cutover. Land the 134px column, 17+2+28px stack, 48px rows / 50px pitch, working Track/Step for all tracks, melodic Notes, lane access, common page gaps and synchronized scrolling together. Reserve dock space; replace the drawer and hidden/dead mobile paths only alongside usable replacements. Verify portrait and orientation transitions.

Each future phase has its own relevant checks and reviewed baselines. Geometry measurements of these mocks validate the proposal; they do not validate application integration.
